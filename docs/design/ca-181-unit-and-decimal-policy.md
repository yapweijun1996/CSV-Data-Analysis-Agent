## Sources of trusted unit meaning

- **Header parsing:** suggest explicit suffixes such as `Amount (SGD)`; cheap and explainable, but ambiguous symbols, abbreviations and inherited report headers cannot establish currency or row consistency. Suggestion only, never authority.
- **User-confirmed semantic review:** bind the measure to either a fixed unit or a specific row-unit column, exact dataset/version and source evidence; invalidate on version or mapping change. Strongest available authority, but requires informed confirmation and can still be wrong. Existing host contract separates resolved meaning from guest assertions (`frontend/services/data/candidateValidation.ts:4-9`); a general confirmation flow for this policy is UNVERIFIED.
- **Dataset profile:** propose candidate unit columns, distinct labels, blanks and coverage over the complete filtered scope; sampling cannot establish absence of mixed units. Useful for discovery, not semantic authority. Existing numeric profiling/parser entry points are in `frontend/services/data/dataProfiler.ts:19-23,74-97`; availability of complete, version-bound unit profiles is UNVERIFIED.

## Proposed policy

1. Bind each measure to a reviewed fixed unit, a reviewed row-unit column, or an explicit reviewed **dimensionless** meaning. Preserve source provenance and dataset/version identity; labels alone, currency symbols or automatically inferred mappings are not trusted. Normalize only owner-approved aliases; no implicit currency or physical-unit conversion.
2. Check all contributing rows after query and aggregate-specific filters, independently for each measure and output group. A numeric NULL does not contribute; if no values contribute, return NULL, not zero. Counts of rows/presence remain unit-independent. A group may sum or average only if every contributing value has one identical trusted unit. For several period columns, each contributing column's trusted unit must also agree.
3. Mixed units: refuse the affected sum/average unless the user requests grouping by the trusted unit; split results must carry the unit in every output key. Never silently insert a group, discard rows, convert or merge currencies. An omitted/untrusted/blank unit on any contributing value blocks that aggregate, even if all other units agree. Offer semantic review or an explicit filter/split; do not treat missing as a unit or infer it from neighbors. Explicit dimensionless values may aggregate only with the same confirmed dimensionless meaning.
4. Re-evaluate every subtotal, pivot row/column total and grand total against its own underlying contributing rows, including hidden/truncated groups. For mixed or missing units, suppress/refuse that total or provide separate unit-labelled totals; safe child groups do not make a mixed grand total safe. Average totals must be computed from the underlying sum and count, not by adding averages; count totals remain unit-independent.
5. **Exact amounts:** for confirmed currency and other exact measures, retain validated base-10 strings and use DECIMAL throughout, including filters, intermediate sums and serialized results; never convert to JS number or silently fall back to DOUBLE. Proposed bounded contract: input precision at most 24 digits, scale 0–6, aggregate/intermediate precision at most 38 digits and scale at most 6. Preserve the highest contributing scale; reject excess nonzero digits, non-representable input, overflow and unsupported route. Actual ingestion and DuckDB/Arrow limits for this contract are UNVERIFIED and must be proven before enabling it.
6. **Average:** calculate exact sum and count, then perform decimal division using an explicit output scale (default max(input scale, 2), at most 6) and round half-even once at the final result; include scale/rounding metadata. Keep sum/count or an exact rational as evidence. Do not assume native `AVG(DECIMAL)` is exact: prove it or implement exact division. Presentation rounding must not feed further totals.
7. DOUBLE is permitted only for explicitly approximate measures or an explicitly labelled approximate analysis, never as an automatic downgrade for a confirmed exact measure. Unknown precision meaning requires review; overflow, missing metadata and unsupported execution fail closed. An approximate mode still enforces unit compatibility.
8. Suggested messages: “Cannot calculate: values have different units. Group by unit or filter to one unit.” “Cannot calculate: unit is missing or unconfirmed. Review the measure and its unit.” “Exact calculation exceeds supported precision or is unavailable on this path; no approximate result was substituted.” Do not expose raw cell values in errors.

Acceptance: mixed-unit groups and totals are blocked or explicitly split; safe groups with mixed-unit grand total never show a combined value; average totals use underlying counts, even with hidden rows. Acceptance: sums and half-even averages agree across supported paths for scale 0–6, negative ties, >JS-safe integers and filtered groups; 38-digit overflow fails without DOUBLE fallback. Each stage needs consumer-level regression tests and actual-path smoke verification; route inventory and exact integration files beyond those listed are UNVERIFIED. Ship fail-closed slices rather than claiming full CA-181 acceptance before all paths are covered.

## Owner decisions (recommended defaults)

1. **Authority:** user-confirmed, version-bound semantic mapping; header/profile suggestions never authorize.
2. **Missing or mixed units:** refuse; allow only explicit unit grouping/filtering, never infer or convert.
3. **Unitless data:** require explicit dimensionless confirmation rather than assuming unknown means unitless.
4. **Exact range and rounding:** precision 24 input / 38 intermediate, scale 0–6, half-even at final average; qualify limits first and refuse otherwise.
5. **Totals and approximate mode:** suppress incompatible totals; allow DOUBLE only when clearly labelled approximate and not for confirmed exact measures.

## Non-goals

No FX rates, unit conversion, automatic semantic approval, broad numeric parser rewrite, raw SQL governance redesign, deployment, or implementation in this design. No claim that existing tests or reviewer reports prove end-to-end acceptance.
